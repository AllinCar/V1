## ۱. نمای کلی محصول

**محوریت:** شارژ سیار خودروی برقی در محل + خدمات مکمل.

- ارزش پیشنهادی هسته‌ای: اجرای بی‌نقص «شارژ سیار».
- خدمات مکمل (هم‌وزن با شارژ نیستند): کارواش، دیتیلینگ، سرویس دوره‌ای، امداد خودرو، راننده/تحویل.
- یک اپلیکیشن واحد برای دو تجربه: **حساب فردی** و **حساب سازمانی** (تفاوت فقط در لایه تجربه).
- شفافیت SLA در هر نقطه انتظار (قیمت، ETA تکنسین، کیفیت).
- گیمیفیکیشن سبک: مسکات/آواتار ثابت + امتیاز ساده.
- پلتفرم: PWA موبایل‌محور (React + Vite)، داده mock در فاز صفر.

> در بیزینس کانواس اصلی، برچسب‌های B2B/B2C وارونه به‌کار رفته‌اند. در این سند همیشه از «فردی» و «سازمانی» استفاده می‌شود.

## ۲. اصول حاکم بر فاز صفر

1. تمرکز کامل روی مسیر رزرو شارژ سیار به‌عنوان مسیر حیاتی محصول.
2. معماری یکپارچه فردی/سازمانی با تفاوت در لایه تجربه (نه دو اپ جدا).
3. گیمیفیکیشن سبک؛ عمق بیشتر فقط یادداشت نقشه راه است.
4. شفافیت SLA در تمام نقاط انتظار.
5. قابلیت نصب/آفلاین به‌صورت PWA برای نمایش موبایل.
6. موبایل‌محور، پشتیبانی RTL/فارسی (و در نسخهٔ فعلی frontend: دو زبانه fa/en).
7. تم تیره Glassmorphism طبق دیزاین سیستم.
8. بدون بک‌اند واقعی در این فاز؛ داده mock.

## ۳. کاربران هدف و ساختار کسب‌وکار

### کاربران

| نوع | مخاطب |
|---|---|
| حساب فردی | صاحبان خودروی لوکس، صاحبان تاکسی برقی |
| حساب سازمانی | شرکت‌های دارای ناوگان، هتل‌ها و رستوران‌ها |
| مهمان (غیرکاربر) | خودروی مهمان هتل/رستوران — فقط لینک پیگیری |

### تفاوت تجربه فردی / سازمانی

| لایه | فردی | سازمانی |
|---|---|---|
| خانه | تمرکز روی یک/چند خودروی شخصی | ویجت نمای کلی ناوگان |
| خودروها | «کارگزار شخصی» با تکنسین ثابت | نمای فهرستی + گزارش‌گیری مدیریتی |
| درخواست سرویس | تکی، فوری یا زمان‌بندی‌شده | درخواست دسته‌جمعی |
| پرداخت | کیف پول شخصی / پکیج فردی | فاکتور رسمی، تسویه دوره‌ای |
| نقش‌ها | یک کاربر | مدیر ناوگان / راننده / حسابداری |
| باشگاه | امتیاز و مزایای فردی | امتیاز تجمیعی سازمان + مزایای قراردادی |

## ۴. بیزینس کانواس

### بخش‌های مشتری
- حساب فردی، حساب سازمانی، حالت مهمان‌نواز (سرویس برای مهمان بدون حساب؛ فقط لینک پیگیری).

### ارزش پیشنهادی
- شارژ سیار ۲۴ ساعته («حتی الان هم می‌تونیم بیایم»).
- خدمات مکمل افزودنی در جریان رزرو.
- شفافیت SLA: قیمت قفل‌شده، ETA، نام/امتیاز تکنسین قبل از تایید.
- کارگزار شخصی خودرو (تکنسین ثابت).
- باشگاه مشتریان + امتیاز + پکیج‌ها.
- پیش‌بینی نیاز (کارت یادآوری بر اساس داده خودرو / الگوی مصرف).

### رابطه با مشتری
- «باشگاه» به‌جای «پروفایل».
- کارگزار شخصی، گیمیفیکیشن سبک، شفافیت SLA، مرکز اعلان‌ها.

### کانال‌ها
- اپ PWA، اعلان درون‌اپ، ردیابی زنده، تماس/چت با تکنسین، لینک پیگیری مهمان.

### جریان درآمد
- قیمت‌گذاری سرویس (kW / درصد / اضطراری)، پکیج و اشتراک، کیف پول، فاکتور سازمانی و تسویه دوره‌ای.

### منابع / فعالیت‌ها / شرکا / هزینه
- ناوگان تکنسین و تجهیزات شارژ، اپ و داده سلامت خودرو، برند/مسکات.
- دیسپچینگ با SLA، جریان رزرو، پیش‌بینی نیاز.
- تکنسین‌های رسمی تخصیص‌یافته.
- هزینه تکنسین/دیسپچ و نگهداری اپ (جزئیات در سند منبع محدود است).

> موارد استنتاجی که مستقیم در فیچرلیست نیامده‌اند در مستندات اصلی با 📌 علامت‌گذاری شده‌اند.

## ۷. فیچر لیست فاز صفر

### ۷.۱ Onboarding
- ثبت‌نام با شماره موبایل + OTP
- انتخاب نوع حساب: فردی یا سازمانی
- مسیر فردی: افزودن خودرو + آدرس‌های پرتکرار
- مسیر سازمانی: ثبت شرکت، اعضا با نقش، Import خودرو
- حالت مهمان‌نواز برای هتل/رستوران

### ۷.۲ صفحه خانه (بالا → پایین)

```
📍 موقعیت فعلی              🔔 اعلان‌ها
انتخاب خودرو: [ماشین ۱ ▾]
🔋 درخواست شارژ سیار (CTA اصلی)
   «حتی الان هم می‌تونیم بیایم»
دسترسی سریع: کارواش | دیتیلینگ | سرویس دوره‌ای | امداد | راننده/تحویل
🧑🔧 مسکات سبک — «منتظر دستور شما هستم»
کارت یادآوری: «باتری خودرو ۱ زیر ۲۰٪ — شارژ سیار رزرو کنید»
```

### ۷.۳ جریان رزرو شارژ سیار (مسیر حیاتی)

1. انتخاب خودرو  
2. انتخاب مکان (نقشه / آدرس ذخیره‌شده)  
3. انتخاب زمان («همین الان» یا زمان‌بندی‌شده)  
4. میزان شارژ (kW / درصد هدف / شارژ اضطراری)  
5. خدمات مکمل اختیاری  
6. نمایش شفاف قبل از تایید: قیمت، ETA، نام/امتیاز تکنسین  
7. تایید و پرداخت  
8. ردیابی زنده: پذیرفته شد → در مسیر → رسید در محل → در حال شارژ → تکمیل شد  
9. پس از اتمام: رسید، امتیازدهی، تاریخچه سلامت، امتیاز باشگاه  

### ۷.۴ خودروها / کارگزار شخصی
- **فردی:** پروفایل فنی، یادآوری سرویس، کارگزار من (تکنسین ثابت)
- **سازمانی:** فهرست ناوگان، فیلتر، درخواست دسته‌جمعی، گزارش‌گیری

### ۷.۵ باشگاه (جایگزین پروفایل)
- سطوح برنز/نقره/طلا و مزایا
- تاریخچه خدمات، پکیج‌ها، کیف پول، کد معرف/دعوت
- اطلاعات حساب پایه در پایین‌ترین اولویت بصری

### ۷.۶ گیمیفیکیشن این فاز
- امتیاز ساده به ازای سرویس تکمیل‌شده
- مسکات ثابت با پیام کوتاه هنگام تپ
- نوار پیشرفت به سطح بعدی

### ۷.۷ سایر بخش‌ها
- مرکز اعلان‌ها و شفافیت SLA
- دکمه اضطراری/امداد همیشه در دسترس
- کیف پول و صورتحساب (سازمانی: فاکتور رسمی)
- مدیریت نقش‌ها (سازمانی)
- کشف پکیج‌ها و آفرها

## ۸. دیزاین سیستم

### ۸.۱ مفهوم و حس بصری
- حس: «آرامش در عین تمرکز و تکنولوژی پیشرفته»
- سبک: Glassmorphism + Minimal Dark UI
- زبان فرم: گوشه‌های بسیار گرد

### ۸.۲ پالت رنگ (توکن‌ها)

```css
--bg-base:        #0A1612;   /* پس‌زمینه اصلی */
--bg-deep:        #0B1F1A;   /* عمق گرادیان */
--surface:        rgba(255,255,255,0.06);
--surface-strong: rgba(255,255,255,0.10);
--glass-border:   rgba(255,255,255,0.12);
--primary:        #00F0B5;   /* سبز نئونی — فعال و CTA */
--secondary:      #6366F1;   /* بنفش/آبی الکتریکی — AI */
--text-primary:   #FFFFFF;
--text-secondary: #94A3B8;
--danger:         #F87171;
```

### ۸.۳ تایپوگرافی
- فونت: Vazirmatn (فارسی) + Inter (اعداد/لاتین)
- H1: Bold، ۳۲–۴۰px، سفید
- H2: Semi-Bold، ۲۰–۲۴px
- Body: Regular، ۱۴–۱۶px
- Caption: Medium، ۱۲px، متن ثانویه
- برند با Tracking بیشتر

### ۸.۴ شبکه و فاصله
- پدینگ افقی صفحه: ۲۰–۲۴px
- Grid: ۴ ستونه، gutter ۱۶px
- Radius: کارت ۲۴–۳۲px، دکمه/ورودی کپسولی (۱۰۰px)، آواتار ۵۰٪

### ۸.۵ افکت‌ها
- Glassmorphism با backdrop blur
- Glow سبز نئونی روی عناصر تعاملی
- گرادیان ملایم سبز تیره → مشکی

### ۸.۶ کامپوننت‌های کلیدی
1. ورودی صدا/چت کپسولی (آماده / شنیدن + waveform)
2. کارت تسک/لیست شیشه‌ای
3. آواتار/مسکات دستیار
4. میانبرهای سریع دایره‌ای شیشه‌ای

### ۸.۷ اصول UX دیزاین
1. شخصیت‌سازی AI برای اعتماد  
2. کاهش بار شناختی با بلاک‌های کوچک  
3. ورودی همیشه در پایین در دسترس  
4. Conversational UI (صوتی + متنی)

| کد | الگو | توضیح |

### اصطلاحات رایج
- اعداد/قیمت: `toLocaleString('en-US')` + «تومان»
- Toast سراسری از context
- شبیه‌سازی تایمر برای ردیابی زنده
- RTL با `dir="rtl"`؛ اعداد لاتین با کلاس `num`
- آیکون داینامیک: `const Ico = Icon[key]` (نه `<Icon[x]>`)

### تصمیم‌های معماری سطح‌بالا
1. تک‌اپ PWA موبایل‌محور — React + Vite؛ ناوبری تب با state (بدون Router در نسخه frontend اصلی)
2. معماری یکپارچه فردی/سازمانی با `accountType`
3. State مرکزی + داده mock — آماده جایگزینی با API
4. لایه بیزینس در memory-bank به‌عنوان منبع حقیقت مشترک
5. PWA کامل با کش آفلاین

## ۱۱. دستورعمل‌های توسعه و ایجنت‌ها

### ۱۱.۱ مقررات ساختاری (AGENTS)

- UI دو زبانه: فارسی (`fa`, RTL) و انگلیسی (`en`, LTR) از طریق `t('key')`.
- هر متن UI باید کلید i18n داشته باشد؛ هاردکد فارسی/انگلیسی در JSX ممنوع (جز نام برند).
- سبک بصری حتماً از توکن‌های `system-design` پیروی کند.
- ناوبری ۵ تب ثابت؛ تب «+ درخواست» برجسته.
- داده mock از `src/data/data.js`؛ state از `AppContext`.
- قبل از پیاده‌سازی هر صفحه، اسکیل `phase-zero` را بخوان.
- قبل از هر تصمیم محصولی/UI، `memory-bank/productContext.md` را رعایت کن.

### ۱۱.۲ قانون i18n

- همه متن‌های قابل‌مشاهده کاربر از `t('key')`.
- کلید همزمان برای `fa` و `en` در `translations.js`.
- داده mock نمایشی هم باید کلید i18n یا `{ fa, en }` داشته باشد.
- لحن خدمتگزار/ایجنت را در هر دو زبان حفظ کن.

### ۱۱.۳ اسکیل‌ها

| اسکیل | کاربرد |
|---|---|
| `system-design` | توکن‌ها، رنگ، تایپو، افکت، کامپوننت‌های بصری |
| `phase-zero` | فیچر لیست، ناوبری، جریان‌ها، تفاوت فردی/سازمانی |

### ۱۱.۴ ایجنت‌ها

| ایجنت | نقش |
|---|---|
| **architect** | طراحی معماری، نگهداری Memory Bank، ثبت تصمیم‌ها |
| **code** | پیاده‌سازی React با رعایت دیزاین سیستم و الگوها |
| **ask** | پاسخ به سؤال‌های فنی/محصولی بر اساس Memory Bank (بدون ویرایش MB) |
| **debug** | شناسایی و رفع باگ UI/منطق بدون شکستن یکپارچگی |

#### قوانین Memory Bank (architect / ask)
1. شروع پاسخ با `[MEMORY BANK: ACTIVE]` یا `[MEMORY BANK: INACTIVE]`
2. ترتیب خواندن: `productContext` → `activeContext` → `systemPatterns` → `decisionLog` → `progress`
3. تغییرات معماری مهم باید در Memory Bank ثبت شوند

#### قوانین code
- RTL/فارسی (و i18n دوزبانه در نسخه فعلی)
- فقط توکن‌های دیزاین سیستم
- کامپوننت‌های تکراری از `components/`؛ اسکرین‌ها در `screens/`
- تغییرات نباید قابلیت PWA را بشکنند

#### قوانین debug
- ابتدا ریشه مشکل را پیدا کن (App، AppContext، CSS، PWA cache)
- پس از رفع: `npm run build`
- الگوهای باگ رایج را برای ثبت در `systemPatterns` پیشنهاد بده
